# 文档维护规范

一份没人看得懂的文档，比没有文档更糟——它会让人以为这里有答案。

本规范只解决三个问题：**写什么、放哪里、怎么写才留得住。**

## 一、什么值得写成文档

| 值得写 | 不值得写 |
| --- | --- |
| 调试了两天才找到的原因 | 一眼能看懂的代码逻辑 |
| 技术选型的权衡过程 | 从别处抄来的教程原文 |
| 硬件改版的原因与影响 | 每天的流水账 |
| 可复现的实验步骤与结论 | 没有数据的"感觉好多了" |
| 新人会踩的坑 | 只有作者自己能看懂的缩写 |

判断标准：**如果三个月后的你需要它，就写。**

## 二、放哪里

```text
docs/                     跨项目的规范、流程、术语
docs/adr/                 技术选型决策（编号递增，永不改写）
docs/reports/             周报、阶段总结、复盘（按时间命名）
docs/templates/           模板
docs/archive/             已归档的过期文档
projects/<项目>/README.md 项目自身的说明（必填四件事）
projects/<项目>/notes.md  项目进行中的调试记录
projects/<项目>/tuning-log.md  调参记录
assets/                   所有文档引用的图片
```

不要新建第七个目录层级。找不到位置就放 `docs/`，并在 [docs/README.md](README.md) 索引里加一行。

## 三、文档头

每份正式文档（`docs/` 下的规范类）文末统一加一行：

```text
文档负责人：@github用户名 ｜ 最后更新：YYYY-MM-DD
```

项目 README 用下面的结构，四件事缺一不可：

```markdown
# 项目名

一句话说明这是什么。

## 目标
做到什么程度算成功，量化指标。

## 当前状态
- 已完成：
- 进行中：
- 已知问题：

## 如何编译 / 运行
可直接复制的命令，含依赖版本。

## 设计说明
关键取舍、框图、引脚表链接。

## 变更记录
指向 CHANGELOG.md 或列表。
```

## 四、Markdown 写法约定

### 基本格式

- 文首一个 `#` 一级标题，全文只用这一个一级标题
- 标题层级不跳级：`#` → `##` → `###`
- 标题前后各空一行，列表与代码块前后各空一行
- 有序列表用 `1.` `2.` `3.`，不用 `1)` 或 `①`
- 强调用 `**粗体**`，不要用斜体表示强调
- 中英文之间加空格：`使用 PID 控制`，不是 `使用PID控制`
- 中文标点用全角，代码与英文内用半角

### 表格优于长列表

对比、参数、引脚、命令说明，一律用表格。表格三列以内最佳，超过五列考虑拆成两张。

### 代码块必须标语言

````text
```c
```python
```bash
```text
````

不加语言的代码块在 GitHub 上没有高亮，也没有复制友好度。

### 图片

```markdown
![舵机阶跃响应对比：旧参数超调 18%，新参数 6%](../assets/servo-step-response-20261124.png)
```

- 放 `assets/`，用相对路径
- 文件名：`<主题>-<类型>-<日期>.<ext>`，全小写加连字符
- 必须有 alt 文本，说明图里是什么
- 单张不超过 1MB，截图先裁掉无关区域
- 不要外链别人的图床，会失效

### 链接

- 仓库内文件用相对路径，不用绝对 URL
- 外链附一句说明它是什么，避免链接腐烂后无从追溯
- 引用别人的结论必须给出来源

## 五、ADR：技术选型记录

有取舍的决策都要留档，格式如下，文件名 `docs/adr/0001-选择主控芯片.md`：

```markdown
# 0001 选择 PY32F002BF15P6 作为主控

- 状态：已采纳
- 日期：2026-11-24
- 决策人：@xxx

## 背景
需要一颗能跑双舵机 PWM + I2C 读取 IMU 的小封装 MCU，成本敏感，交期要短。

## 备选方案
| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| PY32F002B | 成本低、供货稳、封装小 | 资源紧、生态资料少 |
| STM32F030F4 | 生态成熟 | 价格高、缺货风险 |
| GD32E230 | 性能好 | 封装偏大、成本高 |

## 结论
选 PY32F002B。

## 后果
- 算力有限，姿态解算需精简算法或降低频率
- 需自行搭建工具链配置（EIDE + arm-none-eabi）
```

规则：**已采纳的 ADR 不可改写**。结论变了就新建一条，标注"取代 0001"。

## 六、周报与复盘

- 周报每周一次，半页以内，重点写**卡点**和**下周计划**，不是工作流水
- 复盘在事故或比赛结束后一周内完成，重点是**改进项与责任人**，不是追责
- 模板：[weekly-report.md](templates/weekly-report.md) · [postmortem.md](templates/postmortem.md)

## 七、归档

文档满足以下任一条件即归档：

- 描述的项目已结束且无后续维护
- 技术方案已被新方案替代
- 超过一年未更新且仍然引用了已废弃的接口

归档操作：

1. 移入 `docs/archive/`
2. 文件顶部加一行 `> ⚠️ 已归档（YYYY-MM-DD）。现行文档见 [xxx](路径)。`
3. 从 [docs/README.md](README.md) 索引中移除，或在索引里标灰
4. **不要删除**，历史决策的价值往往在出问题时才体现
