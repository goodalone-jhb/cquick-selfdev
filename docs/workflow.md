# 协作流程

本文是 [CONTRIBUTING.md](../CONTRIBUTING.md) 的展开版，补上具体操作步骤和判断标准。

## 一、一个改动从想法到合入

```text
想法
 ├─ 小改动（错别字、注释、单文件 bug）
 │    └─ 直接开分支 → 提交 → PR → 合并
 └─ 有设计取舍的改动（选型、架构、接口）
      ├─ 1. 开 Issue 说清背景与备选方案
      ├─ 2. 组内讨论，必要时写 ADR 到 docs/adr/
      ├─ 3. 达成结论后再动手
      └─ 4. 开分支 → 提交 → PR（PR 里贴 ADR 链接）→ 合并
```

判断标准很简单：**如果你需要向别人解释"为什么不用另一种做法"，那就先写 Issue。**

## 二、日常操作

### 开始一个新任务

```bash
git switch main
git pull
git switch -c feat/servo-soft-start
```

分支名格式：`<type>/<简短英文描述>`。一个分支只做一件事。

### 提交

```bash
git add -p                     # 分批暂存，避免把调试代码一起提交
git commit -m "feat(servo): 加入软启动，限制启动电流冲击"
git push -u origin feat/servo-soft-start
```

### 保持与 main 同步

```bash
git fetch origin
git rebase origin/main         # 私有分支用 rebase，保持历史干净
```

已推送且有人在评审的分支，改用 `git merge origin/main`，不要 rebase 改写别人的评审上下文。

### 开 PR

PR 描述必须包含：

```text
## 改了什么
## 为什么改（背景 / 解决什么问题）
## 怎么验证的（测试方法、数据、截图）
## 影响范围（涉及哪些硬件版本、哪些模块、是否需要重新标定）
## 关联 Issue
```

### 评审

| 角色 | 要做的事 |
| --- | --- |
| 作者 | 回复每条评论；不打算改的说明理由；改完 push 新提交，不要 force push 覆盖评审记录 |
| 评审人 | 24 小时内给出第一次回应；区分"必须改"和"建议"；涉及硬件的改动要求附实测数据 |

评审判定：**必须改** 用 `Request changes`；**建议** 用 `Comment`。
只有一条"建议"时不要阻塞合并，可以在后续 Issue 里跟进。

### 合并

统一 `Squash and merge`，squash 后的提交信息沿用 PR 标题 + 关键要点。

## 三、文档类改动

文档 PR 走轻流程，但仍需 PR：

| 场景 | 要求 |
| --- | --- |
| 修正笔误、改格式 | 可自审，直接合并 |
| 新增文档 | 至少 1 人看一遍，确认没有和现有文档冲突 |
| 修改规范类文档（本目录下的 *.md） | 需要 2 人同意，因为会影响所有人 |
| 归档旧文档 | 需说明替代文档路径 |

## 四、版本与发布

固件按语义化版本打 tag：

```text
v<主版本>.<次版本>.<修订>
v1.2.0
```

| 变更类型 | 版本位 |
| --- | --- |
| 不兼容的接口/协议变更 | 主版本 |
| 新增功能，向后兼容 | 次版本 |
| 缺陷修复、参数微调 | 修订 |

```bash
git tag -a v1.2.0 -m "舵机软启动；修正 IMU 上电时序"
git push origin v1.2.0
```

同时在该项目的 `CHANGELOG.md` 顶部加一节，写清改了什么、影响哪些硬件版本、是否需要重新标定。

## 五、周期性记录

| 类型 | 频率 | 位置 | 长度 |
| --- | --- | --- | --- |
| 周报 | 每周一次 | `docs/reports/YYYY-Www-周报.md` | 半页以内，重点写进展与卡点 |
| 阶段总结 | 每个里程碑 | `docs/reports/YYYY-MM-阶段总结-<主题>.md` | 不限，要有数据 |
| 复盘 | 事故/比赛后一周内 | `docs/reports/YYYY-MM-DD-复盘-<事件>.md` | 按模板，重点是改进项与责任人 |

模板：[周报](templates/weekly-report.md) · [复盘](templates/postmortem.md)

周报不是汇报给谁看，是给未来的自己留证据：当时卡在哪、怎么绕过去的。

## 六、分支保护与权限

`main` 分支规则（由维护人在仓库设置中启用）：

- 禁止直接 push，必须走 PR
- 至少 1 个 approve 才能合并
- 合并前必须通过 CI 文档检查
- 禁止 force push 与删除分支

## 七、紧急情况

比赛前一天发现 `main` 上有致命 bug，允许走快速通道：

1. 直接开 `hotfix/<问题>` 分支修复
2. PR 只要求 1 人 approve，评审侧重"是否会引入新问题"
3. 合并后 48 小时内补写复盘，说明为什么没在测试阶段发现

快速通道是例外，不是常态。一个月用超过两次，说明测试流程有问题，该改流程了。
