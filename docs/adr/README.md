# 架构决策记录（ADR）

这里记录所有**有取舍**的技术决定：选了什么、为什么、放弃了什么、代价是什么。

## 为什么要写

半年后有人问"为什么用互补滤波不用 EKF"，答案不该是"当时那个人说这样就行"。
ADR 让决策过程可追溯，也让后来者知道推翻它需要付出什么代价。

## 什么时候写

| 需要写 | 不需要写 |
| --- | --- |
| 主控/传感器/驱动芯片选型 | 改个变量名 |
| 控制算法路线（滤波器类型、控制结构） | 调一个参数值（进 tuning-log） |
| 通信协议与帧格式 | 修 typo |
| 工程结构与构建方式 | 加一个日志打印 |
| 是否引入 RTOS | |

判断标准：**这个决定如果被推翻，需要改动超过一个模块吗？** 是，就写。

## 怎么写

1. 复制下面的模板
2. 文件名：`NNNN-短横线描述的英文或中文.md`，编号从 0001 递增，不复用
3. 在 [../README.md](../README.md) 索引里加一行

```markdown
# NNNN 标题（一句话说明决定了什么）

- 状态：提议 / 已采纳 / 已废弃 / 被 NNNN 取代
- 日期：YYYY-MM-DD
- 决策人：@github用户名
- 相关 PR / Issue：#12

## 背景
当前面临的问题、约束条件（成本、交期、算力、人手）。

## 备选方案
| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| A | | |
| B | | |

## 结论
选了哪个，一句话说明核心理由。

## 后果
- 正面：
- 负面（必须写，包括后续需要补的工作）：

## 推翻条件
出现什么情况时应该重新评估这个决定。
```

## 规则

- **已采纳的 ADR 不可修改**。结论变了就新建一条，状态写"被 NNNN 取代"
- 负面后果必须如实写，这是 ADR 最有价值的部分
- 决策人可以不是组长，谁做的决定谁签名
